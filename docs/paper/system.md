## 03. MAESTRO

### 3.1 Target Domain: Multimodal GUI Chatbot 워크플로우

- 기존 GUI 서비스에 자연어 에이전트를 내장한 multimodal GUI chatbot
- 고정된 다단계 워크플로우 (영화 → 극장 → 날짜 → 시간 → 좌석 → 확인)
- 각 단계에 대응하는 GUI 컴포넌트: 버튼 그룹(영화), 캘린더(날짜), 좌석맵(좌석) 등
- 뒤로 가기는 가능하지만 순서는 고정 (건너뛰기/재배열 불가)

#### 이중 데이터 모델

각 단계의 옵션은 두 층으로 구성된다:

- **데이터 층 (items)**: 백엔드에서 가져온 전체 속성을 포함하는 내부 표현. 화면에 바로 보이지 않는 속성(러닝타임, 평점, 거리, 종료 시각 등)까지 포함한다.
- **표시 층 (visibleItems)**: 현재 사용자에게 실제로 렌더링되는 요소. 데이터 층의 일부만 선별하여 보여준다.

이 구조는 XML에서 attribute와 보여지는 content가 구분되는 것과 유사하며, 본 시스템은 Google A2UI [TODO: cite]에서 모티브를 얻어 선언적 JSON UI Spec을 커스텀하여 사용한다. 에이전트는 두 층을 모두 관찰할 수 있으므로, 사용자에게 보이지 않는 속성을 표시 층에 투영하거나, 표시 순서·가시성·강조를 조정하는 방식으로 UI를 조작할 수 있다.

- 예: "이 영화 러닝타임이 얼마야?", "가장 가까운 극장은?"
  - Baseline 조건: 에이전트가 관련 정보를 텍스트로 답변
  - MAESTRO 조건: 에이전트가 해당 속성을 표시 층에 반영하여 GUI에 직접 표시

#### 인터페이스 구성: 단일 스트림 vs. GUI–채팅 분리

본 시스템은 두 가지 인터페이스 구성을 사용한다.

**Baseline 조건 — 단일 채팅 스트림**: 하나의 채팅 타임라인에 GUI 스냅샷과 에이전트 메시지가 인라인으로 함께 나타난다. 사용자는 대화 흐름을 스크롤하며 이전 GUI 상태를 확인할 수 있지만, GUI 적응 도구가 없으므로 화면이 동적으로 변하지 않는다. 이 구성에서는 별도의 GUI 패널이 불필요하다.

**MAESTRO 조건 — GUI 패널과 채팅 패널 분리**: 화면을 GUI 패널(좌측)과 대화 패널(우측)로 나눈다. GUI 패널에는 현재 단계의 옵션이 항상 표시되며, 에이전트의 적응 동작(강조, 필터링, 정보 주입 등)이 이 패널에 실시간으로 반영된다. 대화 패널에서는 사용자와 에이전트의 자연어 대화가 진행된다.

이 분리는 GUI 적응의 효과를 극대화하기 위한 설계이다. 적응 도구가 GUI를 동적으로 변경하므로, 사용자가 현재 GUI 상태를 항상 볼 수 있어야 "무엇이 바뀌었는지"를 즉시 파악할 수 있다. 동시에 대화 패널에서 에이전트가 "왜 바뀌었는지"를 설명하므로, 두 패널이 상호 보완적으로 작동한다.

#### 통제된 평가 환경

이 도메인은 웹/모바일 다단계 인터랙션 패턴의 단순화된 추상화이다. 실제 웹에서는 페이지 전환, 필요한 UI 위치 찾기 등의 부가 인지 부하가 존재하지만, 이를 배제하고 adaptation과 exploration steering의 효과만 독립적으로 평가하기 위한 통제된 환경으로 설계하였다.

### 3.2 LLM Agent

MAESTRO의 에이전트는 챗봇 시스템에 내장되어 Perception → Planning → Action → Memory 사이클로 동작한다.

#### Perception (인지)

에이전트는 매 턴마다 다음을 관찰한다:

- **현재 화면 상태**: 현재 단계, 표시된 옵션 목록, 적용된 적응(강조·정렬·필터 등)
- **데이터 층과 표시 층**: 데이터 층에는 GUI에 바로 표시되지 않는 속성(러닝타임, 평점, 거리, 종료 시각 등)이 포함되어 있어, 에이전트는 사용자가 보는 것 이상의 정보를 활용할 수 있다
- **사용자의 자연어 발화**
- **단계별 속성 가이드**: 에이전트는 워크플로우 전체 구조(단계 순서)와 각 단계에서 어떤 종류의 속성이 존재하는지를 사전에 알고 있다. 이 덕분에 사용자가 첫 턴에 "뒷좌석이 좋겠다"라고 말해도 좌석 단계의 선호로 올바르게 매핑할 수 있다.

단, 각 단계의 **실제 가용 옵션**은 해당 단계에 도달해야 관찰 가능하다. 시간 단계에서 좌석 가용성을 알 수 없으므로, 선호를 일찍 말할 수 있지만 충족 가능한지는 나중에야 확인할 수 있다.

#### Action Planning (행동 계획)

에이전트는 매 턴마다 현재 화면에서 사용 가능한 도구 집합 중 하나를 선택한다. 이 도구 집합은 현재 상황에 따라 동적으로 조정된다 (예: 필수 선택 미완료 시 "다음" 미제공, 첫 단계에서는 "이전" 배제).

도구는 크게 두 범주로 나뉜다:

1. **표준 인터랙션 도구**: GUI 요소 선택, 다음/이전 단계 진행
2. **적응/탐색 제어 도구**: 정보 주입(augment), 재배열(sort), 필터링(filter), 강조(highlight) 등. 단계 유형에 따라 사용 가능한 도구가 달라진다 — 리스트 기반 단계(영화, 극장, 시간)에서는 네 가지 모두 가능하고, 캘린더나 좌석맵 단계에서는 강조 중심으로 동작한다.

핵심 설계 결정은 에이전트가 사용자의 의도를 대신 확정하기보다, **단계 수준에서는 GUI 적응으로, 워크플로우 수준에서는 탐색 제어로** 반영한다는 것이다:

- 의도 명확 ("이거로 할게") → 표준 인터랙션 실행
- 의도 탐색적 ("별점 높은 코미디 보고 싶어") → 관련 속성을 표시하고 정렬/강조
- 경로 조정 필요 (현재 옵션이 선호와 충돌) → 되돌아가기 제안 또는 자동 수행

#### Action (행동)

에이전트의 출력은 항상 두 가지를 함께 포함한다 (paired output):

1. **자연어 응답**: 수행한 동작이나 현재 상황을 간결하게 설명
2. **GUI 동작**: 표준 인터랙션(항목 선택, 단계 진행 등) 또는 적응/탐색 제어(augment, sort, filter, highlight, 되돌아가기 등)

#### Memory (기억)

- **Baseline 조건**: 전체 대화 기록과 마지막 GUI 상태만으로 맥락을 유지한다.
- **MAESTRO 조건**: 대화 기록에 더해 **구조화된 선호 메모리(shared preference memory, 3.3)**가 추가로 작동한다. 이 메모리는 사용자의 선호를 구조적으로 추출·갱신하며, GUI 적응(3.4)과 탐색 제어(3.5)가 동일한 선호 상태를 공유한다.

MAESTRO 조건에서는 선호 메모리가 핵심 맥락을 담당하므로, 대화 기록을 최근 턴 위주로 축약하여 전달한다. 이는 대화가 길어질수록 LLM이 중간 맥락을 놓치는 lost-in-the-middle 문제를 완화하는 효과가 있다.

### 3.3 Shared Preference Memory

사용자의 자연어 발화에서 선호를 구조화된 레코드로 추출하여 유지한다. 이 메모리는 GUI Adaptation(3.4)과 Exploration Steering(3.5)이 공유하는 기반 상태로, 두 모듈이 동일한 선호를 참조하여 현재 화면의 표현과 탐색 경로를 일관되게 제어할 수 있도록 한다.

#### 선호 레코드 구조

각 선호는 고유 식별자와 함께 세 가지 속성을 갖는다:

- **id**: 선호의 고유 식별자. 내용 기반으로 결정적(deterministic)으로 생성되어, 이후 적응 이력, 실패 경로 기록, 무효화 판단 등에서 선호를 참조하는 키로 사용된다.
- **description**: 선호의 내용 (자연어 설명)
- **strength**: hard (반드시 충족) 또는 soft (가능하면 충족)
- **relevantStages**: 이 선호가 관련된 워크플로우 단계 목록

```json
[
  {
    "id": "pref_comedy",
    "description": "코미디 영화",
    "strength": "hard",
    "relevantStages": ["movie"]
  },
  {
    "id": "pref_weekend",
    "description": "이번 주말에만 가능",
    "strength": "hard",
    "relevantStages": ["date"]
  },
  {
    "id": "pref_front_row",
    "description": "맨 앞 row 3연석",
    "strength": "hard",
    "relevantStages": ["seat"]
  },
  {
    "id": "pref_curfew",
    "description": "친구 A 밤 10시까지 귀가",
    "strength": "hard",
    "relevantStages": ["time", "seat"]
  },
  {
    "id": "pref_rating",
    "description": "별점 높은 영화 우선",
    "strength": "soft",
    "relevantStages": ["movie"]
  }
]
```

사용자가 새로운 선호를 표현하거나 기존 선호를 변경할 때마다 선호 상태가 갱신된다. `relevantStages`를 통해 특정 단계에서 관련 선호만 효율적으로 조회할 수 있으며, 이후 적응(3.4)과 탐색 제어(3.5)가 모두 이 상태를 공유한다.

**Proactive elicitation**: 파일럿 관찰 결과, 사용자가 선호를 명시적으로 발화하지 않고 바로 선택을 요구하는 경향이 있었다. 이를 보완하기 위해 에이전트가 단계 진입 시 능동적으로 선호를 질문한다 ("이 단계에서 중요한 조건이 있으세요?"). 양쪽 조건 모두 동일하게 수행하되, Baseline은 대화 기록 안에서만 활용하고 MAESTRO는 구조화된 선호 레코드로 저장한다.

**GUI 클릭은 선호로 추출하지 않는다.** 클릭은 단순 GUI 조작이며, 옵션을 선택하는 것은 선호 표현이 아니라 현재 탐색 행위일 수 있다. 자연어 발화에서만 선호를 추출한다.

### 3.4 Preference-Grounded GUI Adaptation via In-Place Operators

#### Design Rationale: 4개 Operator의 도출

GUI 챗봇에서 에이전트가 의사결정을 지원하려면, 기존 워크플로우 UI의 구조를 깨뜨리지 않으면서 정보 표현을 조작할 수 있어야 한다. 기존 정보 시각화와 adaptive UI 연구에서 반복적으로 등장하는 GUI 내 정보 조작 패턴을 분석하면 네 가지 기본 연산으로 수렴한다:

1. **시각적 강조 (Highlight)**: preattentive visual cue를 통한 주의 유도 — 정보를 추가하지 않고 기존 요소 간 시각적 위계를 부여 [TODO: cite]
2. **정렬 (Sort)**: 비교 판단을 촉진하는 가장 기본적인 구조화 — 동일한 집합의 표현 순서를 속성에 따라 재배치 [TODO: cite]
3. **필터링 (Filter)**: 탐색 범위 축소를 통한 인지 부하 감소 — dynamic queries와 faceted search에서 검증된 수단 [TODO: cite]
4. **정보 주입 (Augment)**: in-situ contextual annotation — 인터페이스 구조를 바꾸지 않고 기존 요소에 추가 정보를 오버레이 [TODO: cite]

이 네 연산은 **GUI 구조(레이아웃, 컴포넌트, 네비게이션)를 변경하지 않으면서 정보 표현을 조작할 수 있는 범위**를 포괄한다. 시각적 강조만 하는 최소 개입(highlight)부터 정보를 직접 보강하는 개입(augment)까지 수정 강도의 스펙트럼을 형성한다.

이 네 연산은 경량의 프론트엔드 in-place 수정으로 구현한다. 데이터 층과 표시 층이 분리된 선언적 UI Spec 구조 덕분에, 에이전트는 데이터 층에 포함된 속성을 augment로 표시 층에 드러내고, 표시 층의 순서·가시성·강조를 바꾸는 방식으로 UI를 조정할 수 있다.

#### Preference-grounded policy

이 네 연산은 임의로 선택되는 것이 아니라, shared preference memory(3.3)에 저장된 선호의 종류와 강도(strength)에 따라 두 단계의 정책으로 선택된다.

**Step 1 — Visibility gate**: 선호를 적용하기 전에, 해당 기준에 필요한 속성이 현재 화면에 표시되어 있는지 확인한다. 표시되어 있지 않으면 먼저 **augment**로 해당 속성을 표시 층에 드러낸 뒤 다음 단계로 진행한다.
  - 예: 사용자가 "별점 높은 영화"를 원하지만 화면에 평점이 보이지 않는 경우, 먼저 평점을 표시한 뒤 정렬을 수행

**Step 2 — Strength-based selection**: 속성이 화면에 보이는 상태에서, 선호의 강도에 따라 연산을 선택한다.
- **hard preference** (반드시 충족): **filter**로 반영하여 조건에 맞지 않는 옵션을 숨긴다.
  - 예: "IMAX여야 해" → IMAX가 아닌 극장 배제
- **soft preference** (가능하면 충족): **sort** 또는 **highlight**로 반영하여 선호 옵션을 부각한다.
  - 순서형 속성(평점, 가격, 거리 등) → sort
  - 범주형 속성(장르, 포맷 등) → highlight
  - 예: "별점 높은 영화 우선" → 정렬(sort)
  - 예: "코미디 쪽이 좋아" → 관련 영화 강조(highlight)

이 두 단계는 한 턴에 완료되지 않을 수 있다. augment가 필요하면 첫 턴에서 augment를 수행하고, 다음 턴에서 filter/sort/highlight를 이어서 적용한다.

**highlight의 이중 역할**: 비교 지원뿐 아니라, 에이전트가 특정 항목을 가리키며 확인을 구하기 전 시각적 참조 역할도 한다.
  - 예: "이 상영 시간이 가장 잘 맞아 보여요"라고 말하며 해당 시간대를 강조

#### 개별 연산 설명

**Highlight (시각적 강조)**: 하나 이상의 UI 요소를 시각적으로 강조하여 주의를 유도한다. 전체 옵션 집합을 보존하면서 시각적 위계를 생성한다. 예: 추천 시간대 또는 좌석 구역을 강조하여 참조와 비교를 동시에 지원.

**Sort (재배열)**: GUI 컴포넌트 내 요소를 속성에 따라 재배열한다. 기존 데이터를 활용하며, 가용 집합이 아닌 표현 순서만 변경한다. 예: 영화 목록을 별점 순으로 재배열.

**Filter (필터링)**: 조건에 맞지 않는 요소를 일시적으로 숨기고 하위 집합만 표시한다. 예: 코미디가 아닌 영화를 숨기고 코미디 영화만 표시.

**Augment (정보 주입)**: 기존 UI 요소의 표시 내용에 추가 정보를 주입한다. GUI 구조 변경 없이 정보 밀도를 높인다. 예: 영화 제목 옆에 평점을 표기하거나, 상영 시간대에 종료 시각을 표시.

#### 수정 강도 스펙트럼

- highlight → 시각적 강조만 수정
- sort, filter → 내용 변경 없이 표현 재구성
- augment → 기존 요소의 표시 내용 갱신으로 정보 보강
- 최소한의 시각적 단서부터 내용 보강까지의 설계 공간을 포괄

#### 공통 특성

- 누적 적용 가능 (filter + sort, highlight + augment 등)
- 모든 적응은 되돌릴 수 있음 (초기화 도구로 원래 상태 복원)
- 각 적응 행동은 채팅 기록에 남아 이후 대화에서 맥락으로 활용

### 3.5 Preference-Guided Exploration Steering

Preference-Guided Exploration Steering은 shared preference memory(3.3)를 이용해 현재 경로의 적합성을 판단하고, 충돌이 발생하면 되돌아가기를 제안하며, 실패한 경로를 기록하여 이후 탐색에서 같은 실패를 반복하지 않도록 하는 메커니즘이다.

#### 왜 필요한가 — 실용적 동기

에이전트가 대화 기록만으로 선호와 탐색 상태를 추적하도록 했을 때, 다음 문제를 관찰했다:

- 대화가 길어지면 이전에 언급된 선호를 잊거나 혼동
- 어느 단계까지 되돌아가야 하는지 일관되게 판단하기 어려움
- 이미 실패한 경로를 다시 탐색하는 문제가 발생

별도의 shared preference memory(3.3)를 두면, GUI 적응(3.4)과 탐색 제어가 같은 선호 상태를 참조할 수 있다. 적응은 현재 단계의 GUI 표현을, 탐색 제어는 워크플로우 수준의 경로 적합성과 되돌아가기 여부를 각각 담당하되, 동일한 선호를 기반으로 작동하므로 응답과 계획이 서로 어긋나지 않는다.

#### Conflict detection and dead-end recording

에이전트는 매 턴 응답을 생성할 때, 현재 화면의 옵션과 선호 메모리를 함께 해석하여 **충돌(conflict)**을 감지한다. 예를 들어 좌석 단계에서 "맨 앞 row 3연석"을 만족하는 옵션이 없으면, 에이전트는 이를 응답 안에서 설명하고 되돌아가기를 제안한다.

이 과정은 세 단계로 진행된다:

1. **충돌 감지**: 에이전트가 현재 옵션 중 hard preference를 만족하는 것이 없다고 판단하면, 어떤 선호가 충돌을 일으켰는지 함께 산출한다 (conflict annotation).
2. **사용자 확인 대기**: 충돌을 설명하고 되돌아가기를 제안하되, 사용자가 선호를 완화할 기회를 먼저 제공한다. 이 시점에서는 아직 실패로 기록하지 않는다.
3. **실패 경로 기록 (dead end)**: 사용자가 되돌아가기를 수행하면, 해당 경로를 **실패 경로(dead end)**로 기록한다.

이 지연 기록 방식은 중요한 설계 결정이다. 사용자가 선호를 완화하면 같은 경로가 더 이상 실패가 아닐 수 있으므로, 되돌아가기가 실제로 실행될 때까지 기록을 미룬다.

#### Dead end의 범위(scope) 기반 관리

실패 경로는 단순히 "이 항목은 안 됨"이 아니라, **어떤 선행 선택의 조합에서 실패했는지**를 범위(scope)로 함께 기록한다.

- 예: "Steel Meridian 영화 → Metro 8 극장 → 3월 14일"이라는 경로에서 시간 단계에 적합한 옵션이 없어 실패한 경우, 실패 범위는 `{movie: Steel Meridian, theater: Metro 8, date: Mar 14}`이 된다.
- 이후 같은 영화의 다른 극장을 탐색할 때, Metro 8은 이 영화에서 이미 실패한 극장으로 표시되어 에이전트가 추천하지 않는다.
- 반면, 다른 영화를 탐색할 때 Metro 8은 실패 기록이 없으므로 정상적으로 추천 대상에 포함된다.

이 범위 기반 관리 덕분에 실패 기록이 필요 이상으로 넓게 적용되는 것을 방지한다.

각 실패 경로에는 원인이 된 선호의 식별자(id)가 함께 저장된다. 이 연결은 이후 선호 변경 시 무효화 판단에 사용된다 (아래 "선호 변경과 상태 무효화" 참조).

실패 경로 정보는 사용자 UI에 직접 표시되지 않는다. 대신 이후 턴에서 에이전트 입력에 주입되어, 에이전트가 이미 실패한 항목을 배제하고 남은 대안만을 고려하도록 한다.

#### Deterministic backtracking with alternative counts

되돌아가기가 필요할 때, **어느 단계까지** 돌아가야 하는지를 결정하는 것은 중요하지만 LLM에게 전적으로 맡기기에는 불안정하다. MAESTRO는 이 판단을 돕기 위해 이전 단계별로 남아 있는 대안의 수를 계산하여 에이전트에게 제공한다.

대안 수 계산의 핵심 로직:

- 각 이전 단계에서 전체 옵션 수에서 다음을 제외한다:
  - 현재 선택된 항목 (이미 진행 중인 경로)
  - 실패 경로로 기록된 항목 (이미 시도하여 실패한 경로)
  - 적응 이력에 의해 축소된 범위 (filter가 적용된 경우 필터 결과만, highlight가 전체 유효 집합을 표시한 경우 해당 집합만)
- 결과는 가까운 단계부터 먼 단계 순서로 정렬하여 제공

에이전트는 이 정보를 바탕으로 되돌아가기의 목적지를 결정한다. 예를 들어 극장 단계에 대안이 0개이고 영화 단계에 대안이 1개라면, 극장을 건너뛰고 영화 단계까지 돌아가야 한다.

다단계 되돌아가기를 실행할 때, 에이전트는 목적지 단계를 명시한 **연속 되돌아가기 신호**를 생성한다. 이 신호는 중간 단계를 자동으로 통과하는 데 사용된다 — 에이전트는 중간 단계에 도착할 때마다 목적지에 도달했는지 확인하고, 아직이면 자동으로 다음 되돌아가기를 수행한다. 목적지 단계에 도달하면 신호가 소멸되고 정상적인 선호 기반 평가를 재개한다.

#### 선호 변경과 상태 무효화

실패 경로 기록과 대안 수 계산은 모두 선호의 식별자를 기준으로 관리된다. 따라서 사용자가 선호를 변경하면 관련 상태가 자동으로 재평가된다:

- **실패 경로 무효화**: 실패의 원인이 된 선호가 삭제되거나 hard에서 soft로 완화되면, 해당 실패 경로는 자동으로 제거된다. 예를 들어 "IMAX여야 해"를 "IMAX면 좋겠다"로 완화하면, IMAX 부재로 인해 기록된 실패 경로가 모두 해제된다.
- **적응 이력 재평가**: 특정 선호에 기반한 필터/강조 이력도 해당 선호가 유효하지 않으면 함께 제거되어, 대안 수 계산에 더 이상 반영되지 않는다.
- **이후 적응과 탐색 계획**: 갱신된 선호 상태를 기준으로 다시 생성된다.

이 구조 덕분에 MAESTRO는 사용자의 선호를 고정된 제약으로 다루지 않고, 탐색 도중 계속 수정될 수 있는 상태로 유지하면서도, 현재 화면의 표현과 이후 탐색 경로를 일관되게 함께 제어할 수 있다.
